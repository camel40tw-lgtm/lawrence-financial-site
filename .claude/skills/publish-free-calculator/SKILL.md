# 上架免費試算工具 Publish Free Calculator Tool

把一份產品規格書（MD 檔）變成一個上線的免費試算工具，掛在 `D:\AI\lawrence_financial_site` 的「免費試算」（`tools.html`）頁面下。這個 skill 是從兩次實際建置（`policy-irr/` 保單 IRR 試算工具、`property-invest/` 投資不動產規劃平台）的完整經驗整理出來的，包含流程順序、美術規格對齊方式，以及當時真的踩過、之後修正過的技術地雷。

## 核心原則：五個階段，順序不能跳

1. **審查** 規格書
2. **等待使用者明確同意**（硬性關卡，不可省略）
3. **建置**
4. **上架**：commit → push（部署雲端）→ 確認備份
5. **自我測試**：先跑完數學正確性與使用邏輯驗證，才可以回報完成

前兩次的實際經驗是：階段一沒做完整就開始寫程式，會做出方向錯誤的東西（例如技術棧假設錯誤、範疇抓太大或太小）；階段五沒做完整就回報完成，兩次都真的抓到會讓數字算錯或畫面壞掉的 bug（見下方「已知地雷」）。這五個階段都不是形式，每一個都曾經真的擋下問題。

## 階段一：審查規格書

先完整讀規格書，再對照專案現況（見下方「這個網站的技術現實」），產出一份結構化審查，包含：

1. **技術棧落差**：規格書十之八九會建議 React/Next.js/TypeScript/後端資料庫這類與本站不符的架構——一定要指出來，並建議改用原生 JS（見下方）。
2. **範疇確認**：規格書常常野心很大（MVP 疊 MVP）。列出「這次全做」「這次不做，之後再說」「規格書本身互相矛盾、需要你決定怎麼解讀」三類項目，讓使用者選。互相矛盾的例子：`policy-irr` 規格書一邊說「解約金不得填入多個實際解約年度」，一邊又要求「各年度解約比較表」需要每年都能填解約金——這種矛盾自己判斷一個不會重複計算的合理解讀，並在審查裡講清楚為什麼這樣解讀。
3. **金額精度策略**：預設建議「原生 `Number` ＋ 延遲取整（只在畫面顯示時 `Math.round()`，最後一期／最後一筆直接用剩餘值歸零，不要用公式反推再取整）」，不要引入 Decimal.js 之類的套件，除非使用者堅持。
4. **法規／稅務／保險內容**：規格書內若有具體法規條文、生效日期、稅率——**原樣引用，標註資料來源與更新日期，不自行驗證或杜撰**，並在審查裡明講「這段我沒有查證最新公告，正式上線前請你自己核對」。這是紅線，不能省略這句提醒。
5. **是否適合做成靜態網站工具**：如果規格書要求登入、雲端資料庫、金流、多人協作——明講這在目前純靜態＋Cloudflare Pages＋無後端的架構下做不到，建議排除或列為「需要另立專案」。
6. **技術決策問題**：規格書留白、需要使用者現場決定的設計選擇（例如某個功能兩種可能行為、要不要含某個複雜子功能），用 AskUserQuestion 工具問清楚，不要自己悄悄選一個就動工。

審查輸出格式比照繁體中文、有結構（標題、表格、條列）的規範，最後一定要有「需要您確認的關鍵決策」段落。

## 階段二：等待同意（硬性關卡）

**审查發出後，停下來等使用者回覆，不能自己接著動工。** 即使使用者的回覆很簡短甚至看起來像是在催促，也要先確認關鍵決策都有明確答案（技術棧、範疇、有爭議的解讀）才進入階段三。如果使用者跳過某個問題沒回答，直接針對那個缺口再問一次，不要用預設值悄悄帶過。

## 階段三：建置

### 這個網站的技術現實（開工前務必確認還成立）

- 全站純靜態 HTML／原生 JS／CSS，**沒有建置流程**（無 npm build、無 bundler），Cloudflare Pages 直接部署原始檔案。
- 圖表：`Chart.js`（CDN，帶 SRI `integrity` hash）。
- 美術規格：`DESIGN.md` 是單一真相來源，色彩／字體／圓角／陰影一律用 `assets/design-tokens.css` 的 CSS 變數，不寫死 hex。
- 已有兩個同類型工具可以直接參考程式碼與檔案結構：`policy-irr/`（現金流＋IRR 引擎）、`property-invest/`（多步驟精靈＋多模組計算引擎）。新工具的檔案組織方式、CSS 命名慣例（`--<prefix>-ink`／`--<prefix>-accent` 深色模式變數、`.xxx-card`／`.xxx-btn`／`.xxx-stat` 等元件命名）直接比照這兩個，不要自創一套。

### 建置步驟

1. 新建 `<新工具英文代稱>/` 資料夾（簡短、有意義的 kebab-case 英文名，例如 `policy-irr`、`property-invest`）。
2. 先寫**純函式計算引擎**（`*_calc_engine.js` 或 `*_engine.js`），不碰 DOM，掛在 `window.<EngineName>`。
3. 規格書若有驗收測試案例章節，**照著寫成 `test/*.test.js`**（純 Node `assert`，不需要 `npm install`，比照 `policy-irr/test/irr_engine.test.js` 或 `property-invest/test/property_calc_engine.test.js` 的格式），逐一對照規格書給的期望值。**跑這個測試通過，才可以往下做 UI**——引擎邏輯錯了，UI 做得再漂亮也沒用。
4. 再寫 UI：`index.html`（複製 `policy-irr/index.html` 或 `property-invest/index.html` 的 head／header／footer／深色模式初始化腳本骨架，只改內容）＋ `*_ui.js` ＋ `*_style.css`。
5. 需要 PDF 報告／CSV 匯出／本機儲存的話，直接複製 `policy-irr` 或 `property-invest` 裡對應的實作模式（見下方「已知地雷」的 PDF 段落，不要重新設計一套）。
6. 整合：`tools.html` 新增一張 `.article-card.tool-card`（複製既有卡片改內容）；`sitemap.xml` 新增一筆 `<url>`；`CHANGELOG.md` 依既有格式（`## 版本歷史總覽` 表格加一列＋`## 詳細記錄` 底下加一段完整記錄，含「類型／來源／執行內容／驗證／明確跳過待辦」）補一筆。

## 已知地雷（真的踩過，務必主動避開）

這些不是理論上「可能」發生的問題，是前兩次建置**實際**發生過、當時看起來一切正常但其實是錯的，靠自我測試才抓出來：

1. **深色模式下圖表文字消失**：Chart.js 的顏色是在**建立圖表當下**就寫死成字串，不會隨 `[data-theme]` 屬性變化自動重繪。如果使用者是「頁面已經開著才點深色模式切換」，圖表的圖例／座標軸文字會用舊主題的顏色留在畫面上，在新底色上變成看不見。**修法**：在 `init()` 裡加 `MutationObserver` 監聽 `document.documentElement` 的 `data-theme` 屬性變化，變了就重新呼叫 `renderCharts()`。測試時不能只在頁面載入前就設好深色模式再開頁面（那樣測不出這個 bug），一定要**先用淺色模式打開頁面，再點擊切換按鈕**，這樣才會重現。

2. **深色模式下一般文字看不見**：`assets/design-tokens.css` 的 `[data-theme="dark"]` 區塊**沒有**覆寫 `--navy-900`／`--navy-700` 這些變數本身（其他官網頁面是逐一元件手動加 `[data-theme="dark"]` 覆寫）。如果新工具的 CSS 直接用 `color:var(--navy-900)` 當文字色，深色模式下會幾乎看不見（navy-900 跟深色背景太接近）。**修法**：在工具的最外層容器定義區域變數，例如：
   ```css
   .xxx-main{ --xxx-ink: var(--navy-900); --xxx-accent: var(--navy-700); }
   [data-theme="dark"] .xxx-main{ --xxx-ink: var(--text-main); --xxx-accent: var(--amber-500); }
   ```
   所有標題、標籤、數值文字一律用 `var(--xxx-ink)`／`var(--xxx-accent)`，不要直接用 `--navy-900`。

3. **PDF 報告中文變空白或亂碼**：jsPDF 內建字型不支援中文，`doc.text()` 寫中文字會直接壞掉。**修法**：把報告內容渲染成隱藏的 HTML（固定淺色排版、不跟隨深色模式，走瀏覽器原生字型），用 `html2canvas` 逐頁截圖成圖片再用 `doc.addImage()` 貼進 PDF；圖表可以直接用 canvas 本身的 `toDataURL()`，不需要額外截圖。內容如果會超過一頁高度（例如攤還表 30 列），要把截圖切成多張頁面（見 `addHtmlPageSliced` 的實作），不能整張硬塞一頁。**截圖用 JPEG（品質約 0.92）不要用 PNG**：PNG 對文字/表格這種內容壓縮率很差，同樣內容 PNG＋2 倍解析度可能到 28MB，改 JPEG＋1.5 倍解析度可以降到 500KB 上下，肉眼看不出差異。

4. **跳期／不連續現金流折現算錯**：如果現金流陣列不是「每一期都有一筆、完全連續」（例如保單只填了第 0 年、第 10 年，中間沒資料），千萬不能直接用陣列索引當期數去折現（`(1+r)^index`）——會把「第 2 筆現金流」誤當成「第 2 期」，IRR 算出來會嚴重失真（實際案例：正確答案 2%，算成 21.9%）。**修法**：IRR／NPV 函式要接受一個獨立的 `periods` 陣列（每筆現金流實際對應的期數／保單年度），不要假設陣列索引＝期數。

5. **重構後物件形狀對不上**：如果把「計算結果」在存進某個變數時已經先解開一層（例如 `results[key] = fn().result`），後面讀取的地方又寫成 `results[key].result` 多解一層——會直接讀到 `undefined`。這種 bug 不會在語法檢查（`node --check`）抓到，只有實際跑起來才會炸。**避免方法**：改動一個共用資料結構的「形狀」之後，要 grep 整個檔案裡所有讀取這個變數的地方，逐一確認形狀一致，不要只改寫入端。

6. **本機測試時瀏覽器快取讓修改沒生效**：本機起 `python -m http.server` 測試時，改了 JS/CSS 檔案後，Playwright 瀏覽器可能還是跑舊版（尤其 `<script src="x.js">` 沒帶版本查詢字串時）。**修法**：每次改完程式碼要測試前，幫有變動的 `<script src>`／`<link>` 的 `?v=` 版本號往上加一碼；如果加了版本號還是懷疑沒生效，可以在瀏覽器裡直接 `fetch()` 該檔案內容比對，或整個網址加一個新的 query string 強制重新載入文件本身。

7. **`window.prompt()`／`window.confirm()` 不好測也不好用**：互動式輸入（批次填入金額、建立年度數量）一開始圖快用原生 `prompt()`，後來使用者要求改成正式表單彈窗——原生 dialog 在 Playwright 自動化測試裡也會擋住後續操作（必須手動 `browser_handle_dialog` 才能繼續）。**建議**：只要是需要輸入數字/選項的互動，直接做成跟 `policy-irr` 貼上資料 modal 一樣的正式 `.xxx-modal-backdrop` 彈窗，不要用 `prompt()`／`confirm()`（`confirm()` 用在單純的「確定要清除全部資料嗎？」這種無輸入的二選一還可以接受）。

## 階段四：上架（部署雲端＋確認備份）

1. `cd D:\AI\lawrence_financial_site`，`git status` 確認變動範圍在預期內（新工具資料夾、`tools.html`、`sitemap.xml`、`CHANGELOG.md`、規格書 MD）。
2. 如果遇到 `Unable to create '.git/index.lock': File exists`：先確認**目前真的沒有 git 程序在跑**（`tasklist` 或 PowerShell `Get-Process git` 看不到任何 process），才可以刪除這個 0 位元組的殘留鎖檔——這是 git 自己在錯誤訊息裡建議的復原方式，不是繞過保護機制。如果真的有 git 程序在跑，等它結束，不要殺掉。
3. `git add` 明確列出要加入的檔案／資料夾（不要用 `git add -A`／`git add .`，避免不小心夾帶不該進版控的檔案）。
4. `git commit`，訊息比照 `git log --oneline -10` 抓到的既有風格（`feat: ...`，祈使句，講清楚新增了什麼）。
5. **push 前先跟使用者確認**（除非使用者已經在這輪對話明確說了「幫我 commit 並 push」之類的話，那就不用再問一次）——push 是會影響線上服務的動作，屬於一定要確認的範疇。
6. `git push origin main`。這個網站是接 Cloudflare Pages 自動部署（push 到 `main` 就會觸發），push 成功即完成部署，不需要額外的手動部署指令。
7. **備份**：如果這次的素材完全是「使用者給的規格書 MD＋這次新寫的程式碼」，git push 本身就是備份（有版本歷史、有遠端副本），不需要另外複製檔案。如果使用者另外給了**外部素材**（例如像 `calculator-v2` 那次是從另一個獨立專案搬過來、或給了一包 zip／原始檔案），比照 `CHANGELOG.md` 裡那兩筆的慣例，把「未經修改的原始素材」另存一份到 `D:\AI\_uploads-backup\lawrence_financial_site\<工具名>-source-backup\`（部署目錄之外，避免未整理的原始檔案被公開存取），並在 commit / CHANGELOG 裡註明備份位置。

## 階段五：自我測試（一定要做完才能回報完成）

**不能只做 `node --check` 語法檢查就說完成。** 兩次建置都是靠這一階段的瀏覽器實測才抓到真正會讓使用者看到錯誤結果或壞畫面的 bug（見上方「已知地雷」1、4、5）。完整順序：

1. `node --check` 所有新增／改動的 `.js` 檔案。
2. 跑 `test/*.test.js`，對照規格書的驗收案例章節逐項核對——**全部通過才能繼續**，沒通過就是引擎邏輯有問題，回階段三修。
3. 本機起 `python -m http.server <port>`，用 Playwright 開瀏覽器：
   - 走過工具的完整使用流程（不是只看首畫面），每個關�球步驟後檢查 console 有沒有 error。
   - 用已知會算出特定答案的輸入（規格書測試案例的數字），實際在畫面上操作，核對顯示結果跟預期一致——**不是只看程式碼邏輯合不合理，是真的在瀏覽器裡輸入數字看畫面數字**。
   - 深色模式：**先用淺色模式開頁面，再點擊切換按鈕**（不是預先设好深色再開頁面），確認圖表與所有文字都看得清楚（比照地雷 1、2）。
   - 手機版尺寸（例如 380×900）：確認沒有橫向捲動、排版正常。
   - 如果有 PDF／CSV 匯出：實際點擊產生，檢查檔案大小合理（PDF 幾百 KB 到低個位數 MB 屬正常，超過 10MB 要懷疑是不是忘了用 JPEG 壓縮）、並讀取 PDF 內容確認中文正常顯示、數字跟畫面一致。
   - 測試完清掉本機伺服器 process、暫存截圖／PDF 檔案，不要留在使用者的個人資料夾裡。

全部通過才進入「回報完成」。過程中如果抓到 bug，修完要**重新從頭跑一次**這個階段（不是只重測壞掉的那一項），因為修 bug 常常會牽動別的地方。

## 完成後要回報什麼

簡短，不要整段流程重講一次：

1. 這次做了什麼（一兩句話）。
2. 過程中有沒有抓到並修正真的會影響結果的 bug（如果有，講清楚是什麼、怎麼修的——這是使用者判斷「有沒有真的測過」的重要依據，不要省略）。
3. 明確跳過／之後再做的項目（如果階段一的審查有列，這裡對照確認）。
4. **網址**：主網站免費試算頁面 `https://lawrence-financial-site.pages.dev/tools`，加上這個新工具自己的網址 `https://lawrence-financial-site.pages.dev/<工具資料夾>/`。部署後如果剛 push 沒多久，提醒使用者 Cloudflare Pages 通常要等幾分鐘才會生效。
